# أمان منظومة فيول آب — دليل التشغيل والاستجابة

هذا الدليل يرافق الكود. يشرح ما يحمي النظام، وكيف تُدار الأسرار والنسخ الاحتياطية، وماذا تفعل عند الحوادث. التقرير المفصل بنتائج الاختبارات في `docs/تقرير-الأمان.pdf`.

## 1. طبقات الحماية باختصار

| الطبقة | ما يُطبَّق | أين في الكود |
|---|---|---|
| الدخول | bcrypt (تكلفة 12)، رسائل خطأ موحدة، إيقاف الحساب 15 دقيقة بعد 5 محاولات، حد 20 محاولة دخول في الدقيقة لكل IP | `Security/Primitives.cs`، `Controllers/SecurityControllers.cs` |
| التحقق بخطوتين | إلزامي للمدير ومشرف التشغيل ومن يدير المستخدمين. رموز TOTP (RFC 6238) لا تُستخدم مرتين، و8 رموز استرداد مخزنة كبصمات. السر مشفر بـ ASP.NET Data Protection | `MfaService` |
| الجلسات | جلسة لكل جهاز. رمز وصول 10 دقائق، ورمز تجديد يُستخدم مرة واحدة؛ إن أُعيد استخدامه تُلغى الجلسة كاملة. الإلغاء يسري فورًا. الويب يأخذ رمز التجديد في كعكة HttpOnly + Secure + SameSite=Strict | `Security/Sessions.cs`، `ActorAccessor` |
| الصلاحيات | تُقرأ من قاعدة البيانات في كل طلب. كل نقطة تتطلب دخولًا إلا ما يُستثنى صراحة. فحص على مستوى السجل (السائق يرى رحلاته فقط). لا يمنح أحد صلاحية أعلى مما يملك | `Actor.Require`، `UsersController.Grantable` |
| عزل الشركات | طبقتان: فلاتر EF Core وأختام عند الحفظ، ثم أمان مستوى الصف (RLS) في PostgreSQL بوضع FORCE | `Tenancy.cs` |
| قاعدة البيانات | ثلاثة حسابات: superuser للإدارة فقط، ومالك للترحيلات، وحساب تشغيل بلا DDL ولا DELETE ولا تجاوز لـ RLS. سجل التدقيق وسجل العدادات للإضافة فقط بقادح (trigger) | `DbHardening`، `deploy/db-init` |
| المدخلات | استعلامات EF مُمرَّرة كمعاملات، وحدود طول ونطاق لكل حقل، وكائنات إدخال صريحة (لا mass assignment)، وحد 1 ميجابايت للطلب | DTOs في `CoreControllers.cs` و `Services.cs` |
| الملفات | نوع الملف من أول بايتاته (JPEG/PNG/WebP/HEIC/PDF فقط)، وحجم أقصاه 10 ميجابايت، واسم عشوائي خارج جذر الويب، والتحميل بـ nosniff و CSP sandbox، وصلاحية على العملية نفسها | `AttachmentsController` |
| النقل | TLS 1.2/1.3 فقط، وتحويل HTTP إلى HTTPS، و HSTS، و CSP وبقية رؤوس الأمان، و Swagger مغلق للعامة | `deploy/nginx.conf`، `Program.cs` |
| الجوال | الرموز في Keychain/Keystore، و HTTPS إلزامي في نسخة الإصدار، والنص الصريح مسموح في نسخة التطوير فقط، والنسخ الاحتياطي لبيانات التطبيق معطل | `mobile/lib/api.dart`، `AndroidManifest.xml` |
| المراقبة | سجل أحداث أمنية لا يُعدَّل، وتنبيه داخل النظام للمدراء، وخطاف ويب اختياري لـ Slack/Teams/SIEM، وكشف الهجمات المتكررة | `SecurityEvents.cs` |

## 2. الأسرار

- لا يوجد أي سر في الكود أو في صورة Docker أو في تطبيق الجوال. التطبيق لا يعرف إلا عنوان الخادم.
- الأسرار في ملف `.env` على الخادم فقط (ملف `.env.example` يوضح الحقول)، أو في مخزن أسرار مثل Azure Key Vault أو AWS Secrets Manager أو HashiCorp Vault.
- الخادم يرفض الإقلاع إذا كان `JWT_KEY` ناقصًا أو قصيرًا أو بقي على قيمته المثالية، ويرفض البيانات التجريبية في الإنتاج.
- `appsettings.Development.json` يحوي كلمات مرور قاعدة بيانات تطوير محلية فقط، ولا يُنسخ إلى صورة الإنتاج.

### تدوير الأسرار

| السر | متى يُدوَّر | الأثر |
|---|---|---|
| `JWT_KEY` | سنويًا، أو فورًا عند الشك في تسربه | كل المستخدمين يعيدون الدخول |
| كلمات مرور قاعدة البيانات | سنويًا، أو عند مغادرة من يعرفها | `ALTER ROLE ... PASSWORD`، ثم تحديث `.env` وإعادة تشغيل `api` |
| مفاتيح Data Protection | آليًا كل 90 يومًا. احفظ المجلد `keys` ضمن النسخ الاحتياطي | فقدانه يعطل رموز التحقق بخطوتين المسجلة |
| مفتاح النسخ الاحتياطي (age) | عند مغادرة من يحمل المفتاح الخاص | النسخ الجديدة بالمفتاح الجديد، وأبقِ القديم لاسترجاع النسخ القديمة |

## 3. النسخ الاحتياطي والاستعادة

- **التشفير:** `deploy/backup.sh` يأخذ قاعدة البيانات ومجلدي الملفات والمفاتيح، ويشفرها بـ age إلى مفتاح عام. الخادم يستطيع إنشاء النسخة لكنه لا يستطيع قراءتها؛ المفتاح الخاص يُحفظ خارج الخادم.
- **الجدولة:** يوميًا عبر cron، مثلًا `0 2 * * * cd /srv/fuelup && deploy/backup.sh`. وانسخ مجلد `backups` إلى موقع ثانٍ (منطقة أخرى أو قرص منفصل).
- **اختبار الاستعادة:** `deploy/restore-test.sh <مجلد النسخة> <ملف المفتاح الخاص>` شهريًا، واحفظ مخرجاته كدليل. يتحقق من:
  - البصمات؛
  - استرجاع كل الجداول بالأعداد نفسها؛
  - بقاء RLS والقوادح؛
  - قراءة أرشيف الملفات والمفاتيح.
- **الأهداف المقترحة:** أقصى فقد للبيانات (RPO) 24 ساعة مع النسخ اليومي، ويمكن خفضه بأرشفة WAL المستمرة. وأقصى وقت للعودة (RTO) 4 ساعات.

## 4. خطة الاستجابة للحوادث

**الأدوار:** مسؤول الحادث (مدير التقنية)، ومنفّذ تقني، ومسؤول تواصل مع الإدارة والعملاء.

| الخطوة | ما يُفعل |
|---|---|
| 1. الاكتشاف | تنبيه أمني (داخل النظام أو الخطاف)، أو بلاغ مستخدم، أو خلل. سجّل الوقت ومن اكتشف. |
| 2. التصنيف | **مرتفع:** تسرب بيانات، أو حساب إداري مخترق، أو تسرب سر. **متوسط:** محاولات اختراق متكررة، أو حساب سائق مخترق. **منخفض:** محاولات فاشلة متفرقة. |
| 3. الاحتواء | حسب نوع الحادث (أدناه). |
| 4. الاستئصال | أصلح سبب الثغرة، وحدّث المكتبات، وأعد الاختبارات الأمنية (`tests/security.mjs`). |
| 5. الاستعادة | من آخر نسخة سليمة إن لزم، ثم اختبار الاستعادة، ومراقبة مكثفة لأسبوع. |
| 6. المراجعة | تقرير خلال 5 أيام عمل: ماذا حدث، وكيف كُشف، وماذا تغيّر. |

### الاحتواء حسب نوع الحادث

- **حساب مخترق:**
  1. صفحة «الأمان والجلسات»: «تعطيل»، أو «إنهاء الجلسات».
  2. إعادة تعيين كلمة المرور، وإعادة ضبط التحقق بخطوتين.
  3. مراجعة سجل الأحداث الأمنية وسجل التدقيق لذلك المستخدم.
- **تسرب `JWT_KEY` أو كلمات مرور قاعدة البيانات:** دوّر السر فورًا، ثم أعد تشغيل `api`.
- **نشاط مشبوه من عنوان IP:**
  1. احجبه في الجدار الناري أو في nginx (`deny <ip>;`).
  2. راجع `credential.stuffing` و `access.denied.burst`.
- **فقدان أو فساد البيانات:**
  1. أوقف `api`.
  2. استعد من آخر نسخة، ثم شغّل `restore-test` عليها قبل الإعادة للإنتاج.
- **التزامات نظامية:** إن مُسّت بيانات شخصية، فراجع التزامات نظام حماية البيانات الشخصية السعودي (PDPL) في الإبلاغ مع المستشار القانوني.

## 5. قبل كل إطلاق

- [ ] خط CI `security.yml` أخضر بالكامل. يشمل:
  - اختبارات الوحدة والاختبار الوظيفي والهجومي؛
  - `npm audit` وفحص NuGet وحزم Dart؛
  - gitleaks و CodeQL و trivy.
- [ ] `.env` ممتلئ بقيم عشوائية جديدة، و `SEED_DEMO=false`، ولا متغيرات `BOOTSTRAP_*` بعد أول تشغيل.
- [ ] شهادة TLS حقيقية (Let's Encrypt أو شهادة الشركة)، وفحص الموقع على SSL Labs بدرجة A على الأقل.
- [ ] نسخة احتياطية تمت واستُعيدت بنجاح خلال آخر 30 يومًا.
- [ ] تطبيق الجوال مبني بـ `--obfuscate --split-debug-info` و `API_URL` بـ https.
- [ ] اختبار اختراق خارجي مستقل قبل أول إطلاق إنتاجي، ثم سنويًا.

## 6. ما يحتاج إعدادًا إضافيًا أو خدمة خارجية

| البند | لماذا | ملاحظات وتكلفة تقريبية |
|---|---|---|
| شهادة TLS | لا يكفي الشهادة الذاتية | Let's Encrypt مجانية، أو شهادة الشركة |
| تشفير مفاتيح Data Protection | تُحفظ الآن في وحدة تخزين غير مشفرة على الخادم | شهادة عبر `DataProtection__CertificatePath`، أو Azure Key Vault / AWS KMS (تكلفة رمزية شهريًا) |
| مخزن أسرار | بديل أقوى من ملف `.env` | Azure Key Vault / AWS Secrets Manager / Vault |
| موقع ثانٍ للنسخ الاحتياطي | الحماية من فقد الخادم كاملًا | تخزين كائنات (S3 أو ما يماثله) بقفل الكائنات |
| قناة تنبيهات خارجية | التنبيه يظهر الآن داخل النظام وفي سجل الخادم | خطاف Slack/Teams مجاني، أو SIEM مدفوع |
| جدار حماية تطبيقات (WAF) و DDoS | حماية من الهجمات الكثيفة | Cloudflare أو AWS WAF، وغالبًا مدفوع |
| فحص الفيروسات للملفات المرفوعة | التحقق الحالي من النوع لا يكشف ملف PDF خبيثًا | ClamAV مجاني كحاوية إضافية، أو خدمة مدفوعة |
| إعادة ترميز الصور | إزالة بيانات EXIF وأي محتوى مخفي | مكتبة معالجة صور؛ انتبه لترخيصها |
| تثبيت شهادة الخادم في الجوال (pinning) | حماية إضافية من اعتراض الاتصال | يتطلب خطة لتجديد الشهادة |
| اختبار اختراق مستقل | لا يغني عنه أي اختبار آلي | جهة معتمدة، مدفوع |
| نشر التطبيق في المتاجر | حساب Apple Developer و Google Play | 99$ سنويًا و 25$ مرة واحدة |
