# دليل الإطلاق والتشغيل — فيول آب

يشرح هذا الدليل كيف تُجهَّز البيئة التجريبية ثم الإنتاجية، وكيف تُنشر كل نسخة وتُراقَب، وكيف يُرجَع إلى النسخة السابقة، وكيف يُرفع التطبيق إلى المتاجر. خطوات الأمان مكملة في `docs/SECURITY.md`.

---

## 1. الخادم والنطاق

| البند | الحد الأدنى للتجربة المحدودة (حتى ~100 سائق) | ملاحظة |
|---|---|---|
| الخادم | 4 أنوية، 8 جيجابايت ذاكرة، 80 جيجابايت SSD، Ubuntu 22.04/24.04 | الأداء المقيس في التقرير كان على 4 أنوية |
| موقع الخادم | يُفضَّل داخل السعودية (مثل منطقة Google Cloud في الدمام، أو Oracle في جدة، أو STC Cloud) | بسبب نظام حماية البيانات الشخصية وبيانات العملاء |
| النطاق | نطاقان فرعيان: `staging.<نطاقك>` للتجربة و `app.<نطاقك>` للإنتاج | سجل A يشير لعنوان الخادم |
| المنافذ | 80 و 443 فقط مفتوحة للعامة، و SSH (22) من عناوينكم فقط | فعّل الجدار الناري (ufw) |
| البرامج | Docker Engine 24+ مع Compose، و `age`، و `cron` | `apt install docker.io docker-compose-v2 age` |

## 2. أول تشغيل (تجريبي أو إنتاجي)

1. ضع المشروع على الخادم في `/srv/fuelup`.
2. انسخ الإعدادات:

   ```bash
   cp .env.example .env
   ```

   ثم املأ كل قيمة بـ `openssl rand -hex 32`، وضع `PUBLIC_HOST` و `ALERT_WEBHOOK_URL`.
3. أنشئ مفتاح النسخ الاحتياطي على جهاز آخر غير الخادم، ثم ضع المفتاح العام (`age1...`) في `BACKUP_AGE_RECIPIENT`:

   ```bash
   age-keygen -o fuelup-backup.key
   ```

   احفظ الملف الخاص في خزنة كلمات المرور.
4. الشهادة: Let's Encrypt عبر certbot، ثم انسخ `fullchain.pem` و `privkey.pem` إلى `deploy/certs/`.
5. التشغيل:
   - **بيئة تجريبية:**

     ```bash
     COMPOSE_FILES="-f docker-compose.yml -f docker-compose.staging.yml" deploy/deploy.sh 1.0.0
     ```

     تضيف بيانات تجريبية وحسابات اختبار.
   - **بيئة إنتاجية:**

     ```bash
     deploy/deploy.sh 1.0.0
     ```

     تملأ قبلها `BOOTSTRAP_*` لإنشاء الشركة الأولى ومديرها، ثم تحذفها بعد النجاح.
6. أضف المهام المجدولة (`crontab -e`):

   ```
   0 2 * * *   cd /srv/fuelup && deploy/backup.sh >> /var/log/fuelup-backup.log 2>&1
   */5 * * * * cd /srv/fuelup && deploy/monitor.sh >> /var/log/fuelup-monitor.log 2>&1
   0 3 1 * *   cd /srv/fuelup && deploy/restore-test.sh "$(ls -d backups/*/ | tail -1)" /root/fuelup-backup.key >> /var/log/fuelup-restore.log 2>&1
   ```

   اختبار الاستعادة الشهري يحتاج المفتاح الخاص على الخادم وقت الاختبار فقط؛ الأفضل تشغيله على جهاز آخر.
7. أضف مراقبة خارجية مجانية (UptimeRobot أو Better Stack) على `https://<نطاقك>/health` كل 5 دقائق. هي تكشف توقف الخادم كله، وهو ما لا يكشفه `monitor.sh` من داخله.

## 3. نشر نسخة جديدة

```bash
deploy/deploy.sh 1.0.1
```

ما يحدث بالترتيب:
1. نسخة احتياطية مشفرة. إن فشلت يتوقف النشر.
2. بناء الصور بوسم النسخة.
3. تشغيل النسخة الجديدة.
4. فحص آلي: الجاهزية، ورقم النسخة الصحيح، وصفحة اللوحة، واستجابة الـ API، ونقطة الدخول.
5. إن فشل الفحص يرجع النظام تلقائيًا للنسخة السابقة ويرسل تنبيهًا.

السجل في `.deploy/history.log`.

- إن كانت الصور تُبنى في CI وتُرفع لسجل صور خاص، استخدم `deploy/deploy.sh 1.0.1 --pull` مع `IMAGE_PREFIX=<السجل>`.
- احتفظ بآخر 3 نسخ من الصور على الخادم ولا تحذفها، فهي ما يرجع إليه النظام.

## 4. الرجوع إلى نسخة سابقة

- **تلقائي:** عند فشل فحص النشر (القسم 3).
- **يدوي:**

  ```bash
  deploy/rollback.sh
  ```

  يرجع للنسخة السابقة، أو `deploy/rollback.sh 1.0.0` لنسخة محددة.
- **مع قاعدة البيانات:**

  ```bash
  deploy/rollback.sh 1.0.0 --restore-db backups/<المجلد> <المفتاح الخاص>
  ```

  فقط إذا غيّرت النسخة الجديدة البيانات بطريقة لا تفهمها القديمة. **تحذير:** تضيع البيانات المدخلة بعد تلك النسخة الاحتياطية، فسجّلها قبل التنفيذ.

**قاعدة الترحيلات** (تجعل الرجوع آمنًا دون قاعدة البيانات): كل تغيير في القاعدة يكون **إضافيًا** في النسخة التي تُدخله، مثل عمود جديد يقبل الفراغ أو جدول جديد. الحذف أو إعادة التسمية يتم في نسخة لاحقة بعد أن تستقر السابقة. بهذا تستطيع النسخة السابقة العمل على القاعدة الأحدث.

## 5. المراقبة والتنبيهات

| ما يُراقَب | الأداة | التنبيه |
|---|---|---|
| الخادم كله متوقف | UptimeRobot على `/health` | بريد أو SMS من الخدمة |
| قاعدة البيانات، الترحيلات، مجلد الملفات | `monitor.sh` ← `/health/ready` | الخطاف `ALERT_WEBHOOK_URL` |
| أخطاء غير متوقعة في الخادم | `ErrorReporter` فور حدوثها + `monitor.sh` | الخطاف، مع رقم التتبع (التفاصيل في السجل) |
| امتلاء القرص وانتهاء الشهادة وتأخر النسخة الاحتياطية | `monitor.sh` | الخطاف |
| أحداث أمنية (إيقاف حساب، سرقة رمز، محاولات اختراق) | `SecurityEvents` | الخطاف وتنبيه داخل النظام |

- **السجلات:** JSON سطرًا بسطر، بتدوير تلقائي 10 ملفات × 20 ميجابايت.

  ```bash
  docker compose logs api --since 1h
  ```

  للبحث برقم التتبع:

  ```bash
  docker compose logs api | grep <trace>
  ```

- **ترقية اختيارية:** Sentry لتجميع الأخطاء (خطة مجانية محدودة)، أو Grafana Loki للسجلات.

## 6. تطبيق الجوال

### نسخة اختبار (APK داخلي)

```bash
cd mobile
```

```bash
flutter build apk --release --dart-define=ALLOW_SERVER_CHANGE=true --dart-define=API_URL=https://staging.<نطاقك>
```

- يُوزَّع الملف `build/app/outputs/flutter-apk/app-release.apk` للمختبرين، أو عبر Firebase App Distribution (مجاني).
- نسخة الاختبار تسمح بكتابة عنوان الخادم في شاشة الدخول (https فقط). نسخة المتجر لا تسمح بذلك.

### نسخة المتجر — أندرويد

1. أنشئ مفتاح التوقيع مرة واحدة، واحفظه مع كلمته في الخزنة. فقدانه يمنع تحديث التطبيق:

   ```bash
   keytool -genkey -v -keystore fuelup-upload.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload
   ```

2. أنشئ `mobile/android/key.properties` (غير مرفوع إلى git):

   ```
   storeFile=/path/fuelup-upload.jks
   storePassword=...
   keyAlias=upload
   keyPassword=...
   ```

3. ابنِ الحزمة:

   ```bash
   flutter build appbundle --release --obfuscate --split-debug-info=build/symbols --dart-define=API_URL=https://app.<نطاقك>
   ```

4. Google Play Console (25$ مرة واحدة):
   - التطبيق ← اختبار داخلي أولًا ← ثم مغلق ← ثم إنتاج بنسبة تدريجية (10% ← 50% ← 100%).
   - نموذج سلامة البيانات من `docs/store/data-safety.md`.
   - رابط سياسة الخصوصية.

### نسخة المتجر — آيفون

1. يحتاج جهاز Mac مع Xcode، وحساب Apple Developer (99$ سنويًا).
2. ابنِ:

   ```bash
   flutter build ipa --release --obfuscate --split-debug-info=build/symbols --dart-define=API_URL=https://app.<نطاقك>
   ```

3. ارفع عبر Transporter أو Xcode، ثم وزّع عبر TestFlight للاختبار، ثم قدّم للمراجعة.
4. قدّم لآبل حساب سائق تجريبي للمراجعة على بيئة الاختبار (مطلوب).
5. نصوص المتجر وسياسة الخصوصية في `docs/store/`.

## 7. الإطلاق التدريجي

| المرحلة | من | المدة | معيار الانتقال |
|---|---|---|---|
| تجربة داخلية | 2–3 موظفين في المكتب + 3 سائقين | أسبوع | لا أخطاء حرجة؛ كل الطلبات مطابقة |
| تجربة محدودة | فرع واحد أو 10–15 سائقًا | 2–3 أسابيع | نسبة الطلبات بفروقات غير مفسرة < 2%؛ لا توقف |
| إطلاق تدريجي | 25% ← 50% ← 100% من السائقين | 2–4 أسابيع | استقرار المراقبة، وبلاغات الدعم في تناقص |

خلال كل مرحلة:
- شخص دعم معروف للسائقين (رقم واتساب).
- مراجعة يومية لسجل الأحداث الأمنية والتنبيهات.
- قرار مكتوب قبل الانتقال للمرحلة التالية.
